L'API expose le modèle derrière trois routes précises — /health, /ready, /predict-tabular — chacune avec un rôle et des codes de réponse définis à l'avance, avant même d'écrire une ligne de logique métier.

Pourquoi

Liveness ≠ readiness

Une API de modèle pose une question différente selon le moment : le process tourne-t-il ? (liveness) et le modèle est-il chargé et prêt à répondre ? (readiness). Les confondre casse le monitoring : un orchestrateur qui redémarre le service parce que le modèle met du temps à charger provoque une boucle de redémarrages sans fin.

/health vs /ready. /health répond 200 dès que le process a démarré, modèle chargé ou pas — c'est la sonde de liveness. /ready répond 503 tant que le modèle n'est pas en mémoire — c'est la sonde de readiness, celle qui protège /predict-tabular d'un appel voué à échouer.

Dans src/indusense/api/, trois fichiers séparent les responsabilités : main.py déclare les routes, model_store.py gère le chargement et l'injection du modèle, schemas.py définit les formes Pydantic des requêtes et réponses.

Le contrat

Trois routes, trois réponses

RouteRôleCodes possibles
GET /healthliveness — le process répond200
GET /readyreadiness — le modèle est chargé200 · 503
POST /predict-tabularprédiction sur des relevés machine200 · 401 · 422 · 503

La réponse nominale de /predict-tabular est définie par schemas.py avec quatre champs obligatoires :

proba_panne
probabilité de panne estimée par le modèle, entre 0.0 et 1.0
decision
lecture humaine de la probabilité : "alerte" ou "ok"
model_version
version du modèle ayant produit cette prédiction précise
threshold
seuil de décision utilisé pour transformer la probabilité en decision

POST /predict-tabular — X-API-Key: dev-key
→ {"machine_id": "MACH-07", "readings": [ ... 8 relevés horaires ... ]}

200 OK

  "machine_id": "MACH-07",

  "model_version": "test",

Les quatre champs du contrat sont bien présents ; decision vaut "alerte" car proba_panne (0.5) atteint le threshold (0.5).

Repères

Pourquoi charger le modèle une seule fois

lifespan
le modèle est chargé une fois au démarrage du serveur, pas à chaque requête — sinon la latence exploserait.
Pydantic
valide la forme du corps de requête avant d'appeler le modèle : un payload cassé ne consomme jamais de calcul ML.
/docs
généré depuis les schémas Pydantic et les annotations de route — un changement de code se répercute automatiquement dans la documentation.
